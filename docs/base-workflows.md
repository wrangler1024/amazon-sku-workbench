# Base 后端流程接管

0.25.0 增加独立进程 `python -m amazon_aigc.base_workflows worker`。它使用现有服务的 PostgreSQL 和飞书应用，通过官方长连接 SDK 接收记录事件。浏览器和 Base 公式保持现有接口；不通过原生工作流的 HTTP 节点转发，因此不会消耗被替代流程的原生运行次数。

## 配置与边界

设置 `AIGC_WORKFLOW_CONFIG_FILE`，将自己的规则导出文件只读挂载到容器。文件包含 `base_id`、`base_origin`、`record_table`、`timezone`、`tables` 字段 schema、`workflows`、`writable_fields` 和 `identities`。应用凭证沿用服务环境；规则中不存放凭证。真实租户定义、员工映射和生产证据不进入公开仓库。

运行器只支持新增/修改/条件/日期触发、读取、受限字段更新、分支和个人消息。拒绝 HTTP、任意代码、广播、跨表写入和不在允许列表中的字段。用 `identities` 把导出定义内的旧应用 open_id 映射为经验证的 union_id；不能靠显示姓名猜收件人。

人工审核决定仍由现有评审台提交；事件处理核对操作者当前岗位和小组，禁止人工自审。自动通过仅允许经过后端验证的主管自提免评审路径。Base 本身的字段权限仍需保留；后台拒绝派生动作不等于能撤销任何绕过原有权限的直接编辑。

## 切换顺序

1. 备份数据库、服务镜像、私有规则及原生流程定义。在隔离数据库使用合成记录验证全部业务分支；测试不得连接生产数据库。
2. 在应用后台配置长连接和 `drive.file.bitable_record_changed_v1`，并以同一应用订阅目标 Base 的云文档事件。按飞书文档核对所需权限及资源管理权限；单独建立连接不代表已订阅文档。
3. 部署新 worker，保持控制开关关闭。运行 `seed` 建立当前记录基线，读取 `status` 检查规则哈希。基线不能重复覆盖，不重放历史审核和消息。
4. 关闭被接管的原生流程，保留其定义供回退，再运行 `enable`。启动 `worker` 后检查 `health`、监听连接、事件入库、状态写入、消息回执及定时核对。
5. 对既有受阻提交使用 `recover --record-id ID`，它只处理已存在的提交版本和校验状态，使用版本内的原提交时间，不代替人工审批。与新提交版本不符的旧动作会跳过。

`seed`、`enable`、`disable`、`status`、`health`、`recover` 都是 `amazon_aigc.base_workflows` 子命令。规则文件必须与基线哈希一致；调整配置前关闭进程并评估新的迁移，不直接覆盖已有基线。

## 可靠性与运行检查

事件 ID、版本路由键、节点操作键和收件人通知键分别去重。节点执行前写操作日志，读回核验后推进游标；网络超时可恢复而不重复覆盖已完成状态。通知保存在独立队列，失败按退避策略重试，不回滚业务状态；发送前重新检查版本和相关状态。终态失败保留在 `base_workflow_events`、`base_workflow_runs` 或 `base_workflow_notices`，需监控和处理，不能仅看 worker 存活。

公式变化没有记录事件，待校验记录定期读取公式；每分钟刷新提醒数据，并补偿切换后带真实版本时间的新提审。扫描不能还原缺失的人工审核/撤回操作者及准确事件时间，不用扫描时间伪造这些事实。确保长连接持续在线并监控事件接收、错误和数据差异。

补偿不改变已完成 ERP、制图和首次通过时间。提醒按当地日期和配置时间去重，发送前检查最新截止日期、制图状态与接收人；历史全量通知不会因为部署自动重发。

## 回退

先 `disable` 并停止新 worker，确认队列不再写入，再恢复对应原生流程。不要让两套状态处理器同时写入，也不要用旧数据库覆盖上线后产生的业务。SQL 019 为新增表，旧 API 可继续运行；回退应用时保留事件和通知日志。恢复原生流程依然受企业原生工作流额度限制。

外部寄样通知还需要机器人具备外部单聊能力。外部伙伴须先主动打开机器人并完成使用确认；仅取得 union_id 不代表机器人可以主动建立单聊。配置和首次确认要求以[飞书对外共享说明](https://open.feishu.cn/document/develop-robots/add-bot-to-external-group)为准。
