# 云邮箱模块集成

云邮箱已作为`services/store-mail-web`纳入代码仓库，模块版本0.13.1。它保留自己的网页、Python服务、SQLite存储及邮箱权限，可以独立测试、打包、升级和部署。代码集成不等于现有服务器升级。

## 权限与数据边界

当前云邮箱通过自己的飞书应用识别成员，再执行加入审批、功能权限和整邮箱授权。编辑台身份与云邮箱身份没有自动互通；同名用户不能当作同一授权主体。管理员查看范围与个人消息接收列表分别管理，工作台管理员身份不会直接成为邮箱管理员。

原有`supervisor_access_only`设置继续控制试用范围；本次没有在任何环境修改它，也不恢复已停用的站点分类授权。邮箱授权、个人已读/标记、通知队列、邮件与风险事件继续由邮箱SQLite维护。

邮箱主密钥关系到已有授权码解密和会话签名。未来部署或迁移应一致备份数据库及原主密钥，并核对收件游标、授权、通知和个人状态。不能用旧数据库回滚来覆盖新的邮件及用户操作。

## 开发与发布入口

```sh
npm run dev:mail       # 仅离线演示，临时数据
npm run test:mail      # 临时SQLite与模拟外部服务
npm run build:mail     # wheel和标准Python源码包
npm run package:mail -- mail/v0.13.1
```

前两项依赖uv及模块隔离环境；CI使用Python3.12。打包脚本只读取指定Git提交，输出独立模块归档、SHA-256和commit清单。部署模板位于模块内，不加入现有工作台主compose。完整命令见[模块README](../services/store-mail-web/README.md)。

## 后续单独实施

1. **统一入口和身份映射**：先定义账号绑定、会话交换及撤权规则，保留邮箱级权限；不直接复用另一飞书应用的用户标识，不因进入workbench而自动授予邮箱权限。
2. **店铺及业务关联**：在明确店铺标识和数据范围后，再关联SKU和邮件风险事件；邮件内容不是业务状态的唯一权威来源。
3. **数据库迁移**：单独设计SQLite到目标存储的字段/ID映射、密钥处理、对账、增量切换与回退，包含邮件、读标记、通知、授权和历史审计。

以上三项本次均未实现；现有独立登录及邮件存储方式保留。
