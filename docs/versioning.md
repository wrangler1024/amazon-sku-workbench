# 版本管理

## 单仓库、独立组件、组合发布

- 评审前端：`apps/review/package.json`，tag `review/v0.70.2`。
- 编辑前端：`apps/editor/package.json`，tag `editor/v0.21.1`。
- 后台服务：`pyproject.toml`与`amazon_aigc.__version__`，tag `api/v0.21.0`。
- FBACC：`services/amazon-fbacc/package.json`与`src/index.mjs`，tag `fbacc/v0.3.0`。核验工具版本单独记录于`infra/rates/VERSION`（0.2.0），费率快照为2026-10-31.2；三个版本各自描述代码、工具和规则，不能混用。
- 云邮箱：`services/store-mail-web/pyproject.toml`与`store_mail_web.__version__`，tag `mail/v0.13.1`，独立SQLite与依赖锁；不与editor/API绑定升级。
- 组合基线：根package与`versions.json`，tag `v0.3.1`；表示本次验证过的一组版本。
- 飞书应用/小组件发布号是环境部署元数据，与开源包版本分别记录。不要因共享飞书应用版本变化而改写未变化的评审包版本。

ERP自动建料目前仅为规划模块，不加入`versions.json`运行组件、不分配API/包版本、不建立发布标签。规划文档的v0.1表示文档修订，不代表软件已实现；未来开始实现后再登记独立模块版本。

## 日常开发

`main`保存可构建代码，修改通过短期分支和PR。跨模块需求放同一PR，CI同时验证影响范围。代码、必要测试、配置模板和迁移说明一并提交。

开发以本仓库为代码入口；企业环境标识、权限配置、部署凭证及验收数据保留在私有运维目录。此次初始导入保留了现有生产开发目录，未用符号链接替换它们。后续生产升级应先用私有配置构建、在联调核验产物，再切换部署入口，避免新旧目录长期各自修改。

FBACC 由原公开仓库的确定提交通过 squash subtree 导入，来源见模块`UPSTREAM.md`。后续开发在本仓库模块内进行；原仓库保留历史及既有发布。本轮不做双向自动同步，不改变原仓库或线上部署。导出模块时使用`npm run package:fbacc -- REF`，仅导出该提交的模块追踪文件，保留 MIT 许可证及独立目录结构。

云邮箱由私有仓库确定提交的白名单文件脱敏导入，**不合入私有Git历史**。来源与排除范围见模块`UPSTREAM.md`。新公开版0.13.1与来源基线0.13.0分别记录；代码集成不会自动更新服务器。`npm run package:mail -- REF`仅导出指定提交的公开模块及校验清单。后续开发以本仓库为入口，旧私有部署目录保留，不做双向自动同步。

## 发布步骤

1. 更新发生变化的模块版本、依赖锁文件和CHANGELOG。
2. 更新`versions.json`兼容组合，运行版本检查及完整测试/构建。
3. 检查公开边界并运行凭证扫描；提交后打组件tag和组合tag。
4. 将明确的commit/tag部署到联调，核验身份、权限、任务流转和未保存内容保护。
5. 生产部署记录commit、组件版本、镜像digest、数据库迁移版本、环境配置版本和回退点。

CI只运行测试与构建，不自动发布飞书应用或部署生产。SQL迁移只追加；回退应用代码前核对schema兼容性，不通过恢复旧数据库来覆盖上线后正常产生的业务。
